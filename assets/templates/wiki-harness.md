# MyKnowledge Wiki Harness

本文件是 MyKnowledge 知识库的唯一执行规范。所有 Agent 在整理、查询、迁移、更新 `/wiki` 时，必须以本文件为准。任何 `AGENTS.md` / `CLAUDE.md` 只允许薄引用本文件，不应复制或扩写规则。

## 角色

Agent 是知识库维护者，职责是把零散信息整理为可持续积累、可查询、可迁移、可视化的结构化知识。

## 核心方法

优先解决“怎么找东西”，再反推“放哪里”。分类必须从当前材料和真实查找场景中沉淀，不能从固定模板套用。

Harness 不规定每个主题应该有哪些分类；Harness 规定 Agent 必须如何从材料和使用场景中推导分类，并验证分类是否值得落地为目录。

## 分类依据

Agent 判断分类时，按以下顺序取证：

1. 当前主题已有文件的真实内容、文件名、标题、摘要、链接关系。
2. 用户明确表达的查找场景、使用痛点、整理目标。
3. 当前主题内已经存在的总览页、索引页、导航页。
4. 上级主题内已经稳定运行的组织习惯。
5. Agent 基于材料提炼出的抽象分类逻辑。

## 入口规则

每个页面必须有一个 `primary_entry`，允许多个 `secondary_entries`。

- `primary_entry`：由“用户最可能用什么问题找回这篇材料”决定，决定默认归档位置。
- `secondary_entries`：覆盖对象、模块、场景、状态、时间等交叉找回路径，用于索引、双链、筛选和可视化。
- 默认检索入口优先于模块/对象；模块/对象通常作为辅入口、标签、双链或下一级目录。
- 每个入口必须能转换成一句自然语言找回问题。不能转换的入口，不能落地为目录。

## 入口生成与目录固化

入口先试运行，目录后固化。Agent 整理主题时按以下流程工作：

1. 扫描该主题下已有文件名、标题和内容摘要。
2. 提炼用户可能用来找回材料的问题。
3. 将相似问题聚类成少量检索入口。
4. 给每个入口写清楚边界：什么放这里，什么不放这里。
5. 先写入主题总览页。
6. 当主题鲜明、未来会持续增长、检索价值明确时，可以直接划分目录。
7. 当同一入口达到 5 篇左右时应考虑建目录，达到 8-10 篇时默认建议建目录。

目录只在能降低查找成本时创建，不因为分类存在就创建。

## 主题总览页

长期主题使用 `{topic}.md` 作为轻量总览页。总览页只负责帮助找东西，不承载全部内容。

默认结构控制在三个部分：

1. 这个主题是什么。
2. 我该从哪里找。
3. 当前重要页面。

可选包含相关对象、近期变化、已归档材料。如果总览页维护成本超过收益，说明分类过细或页面过重，应合并入口，而不是继续加内容。

## Metadata

新建或重整页面必须补元数据；旧页面在被整理、迁移、更新时逐步补齐。字段名使用英文稳定值，字段说明和可选值中英双写。

最小字段：

```yaml
---
title: 页面标题
domain: 一级领域
scope: 中间范围
topic: 主题
primary_entry: 主入口
secondary_entries:
  - 辅入口
status: current
date: YYYY-MM-DD
objects:
  - 对象/模块/人/系统/事件
---
```

`status` 只使用以下四类：

- `draft` 草稿：内容正在形成、待确认，不能直接作为最终口径。
- `current` 当前：当前有效，可作为查询、沟通、决策或执行依据。
- `archive` 归档：历史材料，主要用于追溯，不默认代表当前口径。
- `unknown` 未知：旧资料或未整理资料，尚未判断有效性。

## 结构性变更审核

涉及以下任一情况时，Agent 必须先形成整理方案：

- 移动或重命名文件。
- 创建新的主题目录。
- 合并多个页面。
- 删除或归档页面。
- 改动超过 5 个页面。
- 修改主题总览页的检索入口体系。

默认由 Agent 自检，不等待人工审核。只有用户明确要求“先给我看”“等我确认”“不要执行”时，才进入人工审核。

大范围变更优先使用独立 Agent 审核，但不强制每次都多 Agent。自检至少确认：找回问题是否清晰、入口数量是否克制、主入口是否唯一、辅入口是否补足跨路径找回、是否避免复制正文、是否减轻认知负担、是否可渐进维护。

如果 Agent 已经形成结构判断，但本轮基于改动范围、风险或用户目标选择暂不执行，必须在最终回复中明确说明：发现了什么问题、为什么暂不处理、建议下一步怎么做。不能只把这类判断写入文件而不告知用户。

## 发现但暂不执行的问题

保守处理是允许的。Agent 可以选择先修复低风险问题，把移动、重命名、目录固化、批量补元数据等结构性动作留到后续处理。

但凡本轮工作中已经识别出以下问题，且选择暂不执行，必须显式披露：

- 内容页位置不符合当前目录规则。
- 页面缺少或不符合 metadata。
- 主题总览页缺失、过重或检索入口不清。
- 入口体系可能需要调整。
- 存在疑似断链、孤立页、重复页、过时页或应归档页。
- 发现治理规则与实际文件状态不一致。

披露要求：

1. 最终回复必须列出“已发现但暂未处理”的问题。
2. 每个问题必须说明暂不处理的原因。
3. 每个问题必须给出建议下一步。
4. 如果问题会影响后续检索或整理，应写入 `/wiki/governance-log.md`。
5. 如果问题属于结构性变更范围，应按 Log 规则写入 [[log]]。

## 治理细则

当任务涉及 Raw/Wiki 晋级判断、主题总览页/MOC、PARA 辅助视角、轻模板、行动项整理、健康检查或治理记录时，Agent 必须读取并遵循 `/system/wiki-governance.md`。

`/system/wiki-governance.md` 只承载治理细则和推荐内容形式，不替代本文件。治理记录写入 `/wiki/governance-log.md`。

## 呈现层边界

当前初始化骨架不包含呈现层规则。`/wiki` 仍是唯一知识源。

如果用户明确要求生成、更新或导出 HTML、deck、PPT 式页面、演示稿、汇报页、精读页、报告页、海报页、PDF、DOCX 或 PPTX，而当前知识库没有明确的呈现层规则文件，Agent 必须先停止并向用户确认呈现规则、源页面、输出位置和是否允许创建呈现目录。确认前不得生成文件。

日常 Wiki query、ingestion、整理、迁移、metadata 补齐、断链检查和健康检查时，禁止把 `/presentation/`、`/presentation/exports/` 或呈现风格目录作为知识来源。

如果后续用户明确接入呈现层，呈现产物仍不得反向作为 Wiki 查询、整理或问答的知识依据。

## 系统目录边界

`/system/` 只存放知识库治理规则、Harness、Prompt、Registry 元数据和 Skill 说明，不作为工具脚本目录使用。

禁止为完成知识库整理、查询、呈现或一次性维护任务，在 `/system/` 下新增可执行工具脚本，包括但不限于：

- `*.py`
- `*.js`
- `*.ts`
- `*.sh`
- `*.mjs`
- `*.cjs`

如果确实需要长期自动化工具，Agent 必须先提出设计方案，并由用户明确确认工具放置位置、执行方式、输入输出、维护边界和是否纳入仓库。未确认前不得新增脚本或把一次性任务固化为系统命令。

从压缩上下文、交接摘要、其他 Agent 的方案或未完成工作继续执行时，Agent 必须重新读取 `AGENTS.md` 与本文件；如果涉及呈现层且存在单独呈现规则文件，还必须重新读取该呈现规则。不得仅凭交接摘要继续修改规则、目录或产物。

## Query 流程

Agent 回答问题时也必须使用 Harness：

1. 先判断用户问题属于哪个 `domain/scope/topic`。
2. 读取该主题总览页，找到可能的检索入口。
3. 优先读取 `current` 当前页面。
4. `archive` 归档和 `unknown` 未知页面只作为背景或历史。
5. 如果主题总览页缺失，临时从文件名和目录提炼入口。
6. 如果本次查询暴露找回困难，更新主题总览页或记录整理需求。

## Log 规则

结构性变更必须写入 `/wiki/log.md`。包括：创建或修改主题总览页的检索入口体系、新建主题目录、移动/重命名/合并/归档页面、批量补元数据、调整 Harness 规则。

单页错字修正、补一两个链接、小范围内容更新可以不写 log。

## 禁止事项

1. 禁止把固定模板强套到所有主题。
2. 禁止为了整齐创建空目录。
3. 禁止没有主入口就移动文件。
4. 禁止复制正文到多个入口。
5. 禁止把“其他/杂项/未分类/资料”作为长期正式分类。
6. 禁止不读主题现状就直接新建主题。
7. 禁止大规模迁移后不更新链接、metadata、主题总览页。
8. 禁止把主题总览页写成沉重模板。
9. 禁止让 `AGENTS.md` / `CLAUDE.md` 复制 Harness 长规则。
10. 禁止在 Harness 中引用任何外部规范作为依据。
11. 禁止在 `/system/` 下新增可执行工具脚本来完成一次性知识库任务。
12. 禁止在未重新读取 Harness 的情况下承接压缩上下文或其他 Agent 的方案继续执行结构性变更。
